## Details

**D-001 to D-004.** Recorded from the approved technical direction in the P01 brief.

**D-005.** P02 configured only the canonical `site` origin. The deployment mechanism stays deferred: no workflow, GitHub Pages settings, secrets, DNS or `eduardogade.github.io` changes. The old deployment published the separate `eduardogade/eduardogade.github.io` repository; whether the new one does the same is undecided.

**D-007.** P01 moved files with `git mv`, so the history follows each file and the moves are reversible. Authored content moved together with the application because it is in Pelican's format; later prompts migrate it from the archive. The primary restoration mechanisms are the tag `pre-astro-checkpoint` and the external backup, not the archive.

**D-008.** `deploy.yml` built Pelican on every push to `main` and force-pushed the output to `eduardogade/eduardogade.github.io`. With the sources archived, it would have failed on the next push. Archived, it no longer runs, so pushes to `main` deploy nothing and the live site stays as last deployed. The eight placeholder workflows are entirely commented out, so they stay where they are. No replacement workflow was added.

**D-009.** See ISSUE-0001. The active hooks would have added a newline to the archived `CNAME`, run `black` on archived Python files and rejected six empty JSON files. A top-level `exclude: ^_backup/` keeps archived files byte-for-byte without bypassing the hooks.

**D-010.** Every tracked file in `cv/`, `publications/`, `scripts/`, `data/` and `hyperglam/` is an empty placeholder, and their purpose for the new site is unclear. `docs/` holds Pelican-era planning notes. They stay in place until a prompt needs them.

**D-011.** `.gitignore` excludes `brand/bearnard/` on purpose, and the repository is public, so committing masters would publish full-resolution artwork. An untracked second copy adds no protection and invites confusion about which file is authoritative. Options for a later decision: keep masters out of Git and rely on backups and checksums, use private storage, or use Git LFS. Until then, the external backup and `assets/bearnard/SHA256SUMS` protect them.

**D-012.** The nodejs.org release index shows that Node.js 26 entered Active LTS ("Lithium") with v26.13.0 on 2026-10-28. P01 described the local v26.12.0 as "not an LTS release". That was true of that build, which predates the LTS designation, but it wrongly suggested the 26 line was not LTS. Policy: `.node-version` says `26`, so version managers and CI pick the latest 26.x release. `package.json` engines are `>=26.12.0 <27`: from the version validated in P02 up to the next major. The local v26.12.0 lacks the v26.12.1 security release; updating it is the owner's call (KL-06).

**D-013.** P01 used `chore/gusmaolab-foundation-p01` and P02 uses `chore/gusmaolab-astro-foundation-p02`. The annotated tag `pre-astro-checkpoint` marks the original state. All are local only. P03 used `feat/gusmaolab-design-system-p03`; from P04, D-035 replaces per-prompt branches with `development`.

**D-014.** The old README documented the Pelican build. Leaving it at the root would have misled readers once that build was archived. P02 expanded the new README with prerequisites and commands.

**D-015.** Astro 7.4.8 is the current stable release: npm `latest`, published 2026-11-09, not deprecated. It requires Node `>=22.23.4` and npm `>=9.6.5`. It is pinned exactly, so upgrades are deliberate decisions.

**D-016.** npm ships with Node.js, and no other package manager is installed. `npm ci` installs exactly what the lockfile records; P02 verified this in an empty copy. `.gitignore` no longer ignores `package-lock.json`.

**D-017.** `astro check` needs `@astrojs/check` and `typescript`. `@astrojs/check` 0.9.12 accepts TypeScript `^5 || ^6`, so the current latest TypeScript, 7.0.2, cannot be used yet. 6.0.3 is the latest 6.x release. `tsconfig.json` extends `astro/tsconfigs/strict`, following Astro 7.4.8's official minimal example.

**D-018.** Static output is Astro's default and matches D-002. `site` sets the canonical origin. The site is served from the domain root, so there is no `base`, even though the source repository is named GusmaoLab.

**D-019.** P02 created `src/pages/`, `src/layouts/` and `tests/smoke-test.mjs`. `src/components/`, `src/styles/` and `public/` will be created when something needs them: nothing does yet, and Git cannot track empty folders. Astro treats `public/` as optional. The homepage is intentionally plain, with no CSS. P03 later added `src/styles/` and `src/design/` (D-026, D-032), and P05 added `src/components/` (D-043); `public/` still does not exist.

**D-020.** No React, Vue, Svelte, Tailwind, Bootstrap, UI kits, Three.js, animation, calendar, Quarto front-end or icon packages. Each needs a feature decision first.

**D-021.** `npm install` briefly upgraded Prettier to 3.9.10 within `^3.6.2`. It was pinned back to the 3.6.2 already in use, so formatting behavior stays the same. Without `prettier-plugin-astro`, Prettier does not format `.astro` files. Revisit when components arrive.

**D-022.** npm 11.20 holds back install scripts until they are approved. fsevents, a macOS file watcher that Vite uses, has an implicit `node-gyp` build script, and its prebuilt binary loads without it. `allowScripts` in `package.json` records the denial.

**D-023.** `LICENSE` is the GNU AGPL v3, while `package.json` said `ISC`, npm's default. `SEE LICENSE IN LICENSE` avoids choosing between `AGPL-3.0-only` and `AGPL-3.0-or-later` on the owner's behalf.

**D-024.** Astro's base preset includes every file under the root and allows JavaScript. Excluding `_backup`, `brand` and the private folders keeps archived and private files out of diagnostics. The empty placeholder scripts in `hyperglam/` and `scripts/` are still included.

**D-025.** The owner authorized deleting obsolete recruiter-related material, which is in the external backup. Both files were confirmed byte-identical there and removed with `git rm` in `d94f170`. Their exposure in the public history remains open as ISSUE-0003.

**D-026.** The P03 brief asked for `tokens.css`, `environments.css` and `global.css`, native CSS, and no Tailwind, Sass, CSS-in-JS or component framework. The layers are primitives (`--palette-*`), semantic tokens and aliases. Aliases are declared on `:root, [data-environment]`: a custom property is computed where it is declared, so a derived token declared only on `:root` would keep its core value inside an environment. BaseLayout imports the three files in cascade order. The structure is approved; the values are not (D-028–D-030).

**D-027.** Every environment defines exactly the 33 tokens of `ENVIRONMENT_TOKENS` in `src/design/contract.mjs`, and `:root` defines them as the core environment. `BaseLayout`'s `environment` prop sets `data-environment` on `<html>`; any element can carry the attribute for a nested scope. No JavaScript theme system and no light/dark toggle. Which section uses which environment comes from the P03 brief for now; P04's route data decides it for real pages.

**D-028.** The brief's suggested colors were kept where they worked (espresso, chestnut, warm brown, muted honey, parchment, warm ivory, charcoal, midnight navy). P03 chose forest `#3D6B2F` from the hue of Bearnard's eyes and added ember, kraft, gold, text tiers, a navy family, spruce, ash and two flannel grounds. Hex values were sampled read-only from the v1.3 master as references, not as specifications. The bear-pride stripes are palette interpretations, not certified flag values. Details and open questions: `planning/design-system.md`.

**D-029.** Seravek for interface and body, Iowan Old Style for editorial text, Superclarendon for display, the system monospace for code and STIX Two Math for MathML. All are installed system fonts, so nothing is downloaded, bundled or redistributed, and the build has no font files. The trade-off: other platforms fall back to close relatives (KL-15). BD Plakatbau, the _Kid A_ reference, is proprietary and unlicensed here, so it was not used.

**D-030.** The flannel is layered CSS gradients (a twill plus warp and weft stripes), scaled by `--texture-flannel-strength`, with `--color-backdrop` as its plain fallback. No image files, no animation, no fixed attachment, and never text on it. It is dropped under `prefers-contrast: more`, `forced-colors: active` and in print. Paper surfaces are flat colors with edge highlights and warm shadows; no paper grain yet.

**D-031.** The thresholds are 4.5:1 for body text and 3:1 for essential non-text indicators, on opaque pairings, in every environment. Disabled text is reported but exempt. Focus uses the same tokens in every environment: a 3 px navy ring on paper and a honey ring on dark surfaces, 2 px offset. Passing the test is not accessibility compliance (KL-17, KL-19).

**D-032.** `npm test` runs three scripts with no test framework: `tests/design-tokens.mjs` (token architecture), `tests/contrast.mjs` (WCAG ratios) and `tests/smoke-test.mjs` (build output). They share `src/design/css-tokens.mjs`, which resolves `var()` and `color-mix(in srgb, …)` as the browser does, and the contract in `src/design/contract.mjs`. The specimen uses the same reader, so the values it shows always match the CSS. The smoke test now checks structural invariants instead of exact text and sizes. It also compares every output file with the Bearnard checksums.

**D-033.** The P02 foundation page is replaced by a specimen, clearly labeled temporary, so the owner can review the visual language before P05–P09 build on it. Its layout styles are scoped to the page and leave with it; the real homepage composition is a later prompt. Superseded in P06 by D-055: the specimen moved, unchanged, to `/_design/tokens/`.

**D-034.** The Claude desktop app starts local preview servers from `.claude/launch.json`. `astro-preview` serves the built `dist/` on port 4322, and `astro-dev` runs the dev server on 4321. Both set `ASTRO_TELEMETRY_DISABLED=1` (KL-14). Other tools can ignore the file.

**D-035.** Separate milestone branches suited preservation and setup, but not routine work. Ordinary prompts now start from the verified `development` HEAD, implement one milestone, validate it and commit with the prompt ID, then continue on the same branch. No `feature/pNN` branches. An `experiment/<topic>` branch (for example `experiment/nucleus` or `experiment/scheduling`), or a worktree, is only for independent, high-risk work that needs isolation. **D-059.** Each preview is built with the page, inside its tab's `<li>`, right after the tab's link and never inside it: a `<div popover="manual">` holding a title and a `<ul role="list">` of plain links (spans in design studies). **D-060.** `src/scripts/folder-previews.ts`, imported once by `FolderStack`, is the site's first client-side script: 2.75 KB minified, which Astro inlines as one `<script type="module">` in every page with folders. It never navigates, touches history or stores anything. Behaviour:

- **Pointer** (mouse or pen): entering an eligible tab opens its preview at once. Moving to another eligible tab switches after 90 ms, so a pointer crossing a neighbour on its way into a card does not switch. Leaving the tab and its card closes it after 120 ms, so the seam between them never makes it flicker.
- **Touch** is ignored: a tap follows the tab's link exactly as without the script, so there is no two-tap trap. Deeper folders stay one tap away in the visible rows.
- **Keyboard:** keyboard focus (`:focus-visible`) on an eligible tab opens its preview without moving focus; Tab then reaches its links, and focus leaving the tab and its card closes it. A click focuses without opening. No focus trap, no arrow-key model, no positive `tabindex`, no `aria-expanded` or menu roles: the links are ordinary links in document order.
- **Escape** closes the open preview; if focus was inside it, focus returns to its tab first. The preview stays closed until both pointer and focus have left the tab, so Escape is never undone by the focus that remains.
- **One at a time:** opening one closes the other; replaced previews also return focus to their tab if it was inside.
- **Leaving the page** (`pagehide`) closes it, so a page restored by Back starts closed.

This replaces the "no client-side JavaScript" clause of D-054 and of the architecture; tabs remain plain links, and NAV-031 now checks that navigation needs no script and that this module is the only one.

**D-080. Routes, ownership, publication state and URLs.**

- **Entries are content routes** (D-039) owned by their collection's folder. They never enter the registry, get no tab and add no row: at most three, whatever the URL length.
- **Public URL = owner path + slug.** The entry ID (the file path) is internal; the title never enters the URL; changing either never moves a page, and publishing a draft never changes its address. A slug is one segment, so the deepest entry URL is one segment below its folder. Deeper Kosmos work and chapter URLs are an extension that needs the owner's approval; none is built.
- **State decides route generation.** Draft: no page in a build. Published: a page and an index entry. Archived: the same URL, listed and marked historical. `astro dev` alone also serves drafts, at their future URL, with a notice and never in an index.
- **Clashes fail the build:** two entries of one collection with one slug (whatever their status), a route that equals a folder's path or lies outside its owner, a repeated sequence place.
- **One mechanism.** The three existing route files list `pageStaticPaths(level)`, folders then entries; `FolderPage` resolves through `getSiteNavigation()`. No catch-all, no router, no hydration; the P09 cross-fade is unchanged. This replaces the planned separate route files under static segments (`planning/information-architecture.md`, section 12).
- **Smoke test:** a page beyond the registered ones is accepted only if it declares itself a published or archived entry at its collection's prefix plus its slug.

**D-084. Identity and time.**

- **IDs** are `<family prefix>-<lowercase-kebab-name>`: `person-`, `organization-`, `area-`, `project-`, `publication-`, `appointment-`, `education-`, `activity-`. Unique across all records, so a bare ID is enough for a cross-reference and its family is evident. Never derived from a title, a list position or private information.
- **ID, slug, route and visibility are four things.** A record creates no page; `slug` (projects) only reserves an address.
- **Dates keep their precision:** `YYYY`, `YYYY-MM` or `YYYY-MM-DD`, as text. A year is never expanded to 1 January.
- **Periods:** optional `start` and `end`; `end: "present"` asserts an ongoing state; a missing end is unrecorded and never displayed as present. An end is an error only when certainly before the start, compared as far as both are known. Overlaps are allowed.
- **Order:** a less precise date sorts where its period begins (`2022` < `2022-01` < `2022-01-01`), so year-only entries follow the dated ones of their year in newest-first lists. Every order ends with the ID.

**D-085. Relationships.**

- **By stable ID, validated for the whole dataset:** existence, the right family, no repeats, no self-reference, and no loop in the one declared hierarchy (an organization's `parentId`). Other relations form a graph and may be mutual.
- **One authoritative side.** An output names its projects and areas; the project's outputs are derived. No relationship is written twice.
- **Authors** are an ordered list, never sorted: `{ personId, as? }` for a registered person (`as` is the name as printed) or `{ name }` for an external credit, which needs no person record. An author is not automatically a profile: `profile` is a separate, explicit field, `none` by default.
- **Output status and type:** `submitted`, `accepted`, `preprint`, `published`; the `preprint` type and status go together; a preprint and its article are two records linked by `related`. Nothing is merged by title, and no metadata is fetched from a DOI.
- **All-or-nothing:** every problem is reported with the record's ID, and an invalid dataset fails the build. A record that fails its schema is reported once; references to it are not reported again as missing.

**D-086. Selectors, projections, citation, visibility.**

- **Path.** The brief names `cv/CV.proposta.yaml`; the file is at `cv/codex-yaml/CV.proposta.yaml`. It was not moved. `cv/manifest.json` records where it is.

**D-090. Authoring and publication are separate.**

- **Five states:** working proposal; versioned working document; author-reviewed version; approved public snapshot; published projection. Only an explicit act of the owner moves a CV from one to the next.
- **`fonte_de_verdade: true` and `situacao` are the file's statements about itself.** They are reported by the tool and read by no code that decides publication. Neither is the file name, nor how complete the file looks.
- **`cv/manifest.json`** names `workingFile`, `published` and `publishEnabled`. JSON, because it is read by the tool and by tests without a parser, and the repository's hooks already check JSON.
- **An approval** needs all of: `publishEnabled: true`; a file named `CV-vX.Y.yaml` that is not the working file; its SHA-256; its version, equal to `metadados.versao`; the approval date. A file edited after approval no longer matches its fingerprint and is refused.
- **No automatic selection.** No code lists a directory; the newest file is never picked; a working file is never promoted; nothing is renamed, and no version metadata is altered to match a name.
- **Version consistency** between a file name and `metadados.versao` is a warning for the owner. `1.0` and `1.0.0` agree. The version is read from the file's text, because a parser turns an unquoted `1.0` into the number 1.
- **Two validation layers.** Authoring validation tolerates everything a draft has and reports only what stops the file from being read. Publication validation decides field by field and record by record. The file is never rejected whole because placeholders remain.
- **Today:** `published: null`, `publishEnabled: false`. Nothing of the CV is published.

**D-091. Text as written; explicit identity.**

- **The CV states many facts as one line** (`instituicao_e_local`, `autores`, `veiculo_e_detalhes`, `curso_carga_e_instituicao`). Splitting them would be guessing, so the record schemas gained fields that hold such a line unchanged: `authorsText`, `authorshipNote`, `creditedTo` and `details` on outputs; `institution` and `department` on appointments; `institution` and `supervision` on education; `context` on every activity; `grantor`, `topic`, `duration`, `subject` where an activity needs them.
- **Either the structured form or the text, never both:** `authors` or `authorsText`; `organizationId` or `institution`; `venue`, `volume`, `issue`, `pages` or `details`.
- **Author lines are never split.** Order, initials and co-first-author asterisks are kept, with their note. `creditedTo` says whose output it is without parsing the line.
- **Statuses the CV does not state are not stated:** an education's `status`, a mentorship's kind and a presentation's kind became optional. A degree's dates are its period as written.
- **New values:** output type `conference-abstract`; appointment type `consulting`; activity types `participation`, `funding`, `training` and `certification`; service types `administration` and `examination`. Funding is an activity, not a ninth family: the CV's grants have the same shape as its awards.
- **Identity.** The CV's identifiers (`4.1.1`, `exp_1`) follow its numbering and may change. They are kept in `provenance.sourceId` and never rewritten. Permanent record IDs are assigned by hand in `cv/identities.json` (`<list>/<source id>` → record ID), validated for family and uniqueness. An ID is never derived from a position, a title or a DOI; a record without one is not projected. Deriving IDs from the section numbers was rejected for the reason the brief gives: section order can change.
- **Structuring later** (authors into people, institutions into organizations) is a deliberate, reviewed conversion, not part of this.

**D-092. Adapter and snapshot.**

- **The adapter** (`src/cv/adapter.ts`) is a pure function from the parsed CV to P11 record shapes and the owner's profile. It changes none of its input. Every kept record is checked against its family's schema.
- **Publication rules:** an unresolved placeholder leaves an optional field out and a record without a required field out; an unknown end is no end and is never "present"; an impossible date is left out, never corrected; an unresolved identifier is not a DOI; a draft (`situacao: Rascunho…`) and a record without an identity are left out. Everything left out is reported, by identifier.
- **Unapproved output is hidden and unreviewed:** without an approval the adapter's records could not be shown even if they were loaded. With one they are `public` and `verified`, and name the approved version.
- **Software** (`software_e_metodos`) yields relationships only: its `evidencia` adds the site's project to those outputs' `projectIds`. The CV does not create or describe a project, so a short CV sentence cannot replace the site's own description.
- **The snapshot** (`src/data/cv/snapshot.ts`) is what a build reads: derived records, profile, version, approval date and the file's SHA-256. It is generated by `npm run cv:snapshot`, never edited, and re-validated when the site loads. It is a derivative, not a second source.
- **Why a committed snapshot:** the CV is private and absent from GitHub Actions, and a build must be reproducible without it. A build-time read of the CV was rejected for that reason.
- **Not generated in P11-A01.** `CV_SNAPSHOT` is `null`; the site builds without CV data. The real file was adapted only in memory, with throwaway IDs, to confirm that its structure is handled: 181 of its 186 list records map and validate, with the owner's person record; the other five are two drafts and three software entries that name no project the site has. Nothing of that run was written.
- **Skills, languages and keywords** are a profile (`siteCv.profile`), not records. Skill groups the author still marks as to be classified or confirmed are left out.
- **The tool is not part of a build.** `cv:check` and `cv:snapshot` are run by hand. Their output carries counts, identifiers and reasons, never the CV's text.

**D-093. Privacy.**

- **The repository is public.** A file that Astro does not publish is still public once committed. The CV files were untracked, not ignored, and have never been committed or pushed.
- **Ignored by Git:** `/cv/codex-yaml/` and `/cv/CV*.yaml`. **Confirmed by the owner on 2026-11-14** ("Keep ignored"). It began as Claude Code's safeguard, not in the brief: the working file holds a telephone number, an email address and third parties' historical email addresses, and one `git add -A` by any agent would publish them irreversibly. It changes no file of the CV workflow. If the owner wants a CV file in Git after all, they record that decision and remove the line; CV-020 says so when it fails.
- **Ignored by Prettier**, so `npm run format` cannot rewrite a CV file.
- **Tracked in `cv/`:** `manifest.json`, `identities.json`, `README.md` and the two empty files from the first commit. CV-020 fails for anything else.
- **Never projected:** the sections `declaracoes`, `cartas_de_apresentacao`, `referencias`, `topicos_master_sugeridos`, `placeholders_pendentes`; `modelo_sem_vinculos` and `texto_sem_vinculos` (writing templates, not statements); `fonte` and `fonte_identificador` (they name private documents); `email`, `telefone`, `localizacao`; `orientando` and `avaliacao_final` (another person's name and grade); `valor_e_condicoes`; unconfirmed teaching hours; `tecnologias`; `experiencia_declarada`; the title of a proposal reviewed in confidence.
- **Contact** is released field by field in the approval, and only public profile links can be released: `orcid`, `lattes`, `linkedin`, `github`, `google_scholar`, `site`, `researchgate`. An email address, a telephone number and a location cannot be published through this path at all; the Contact page is a separate decision.
- **For the owner's review at approval:** the names of candidates in examination boards and of supervisors are projected, as is usual in an academic CV. The snapshot's diff shows every one before it is committed.
- **No push** (D-082): P11-A01 adds integration code and no content; `origin` was not contacted.

### D-094 to D-097 — Editorial reading layouts (P12, P12-A01)

**D-094.** P10 made eight collections that share one pipeline. P12 gives each its own reading experience without eight templates.

- **Shared:** `EditorialArticle` (`src/components/editorial/`) is the one article shell: header (overline, the page's one `<h1>`, description, metadata, tags, notices), the Markdown body, an optional table of contents, a slot after the body, previous and next links, the way back, related entries. - **Style:** `src/styles/editorial.css`, one sheet, `.ed` and `.ed--<collection>` for articles, `.ed-index--<collection>` for indexes. Semantic tokens only; widths and spacing are the editorial tokens at the end of the space section of `tokens.css` (`--measure-reading-*`, `--space-reading-*`). Layout answers to the width of the paper through container queries, since the folders already decide that width. - **Folder pages:** a folder that owns a collection shows `CollectionOverview` (its name as `<h1>`, its one-line identity, its index or an empty state) instead of the P06 scaffolding. `editorial.css` is imported by `FolderPage`, so every page shares one stylesheet set (RESP-013).

**D-095.** New optional fields, all absent from every existing entry, so nothing published changes: `related` (every collection: `<collection directory>/<slug>` references, checked at build time; a reference to a missing entry or to the entry itself fails the build, drafts included, and only published targets are linked), `seriesTitle` (Trail, needs `seriesId`), `chapterLabel` (Kosmos: the author's own mark such as "IV" or "§", shown instead of "Chapter N", never derived), `epigraph` and `epigraphSource` (Kosmos and Months' Original; a source needs an epigraph), `spoilers` (Book Club, default false: a visible note, no hidden content). Related entries are never inferred from tags, years or titles.

**D-096.** `src/editorial/reading.ts` holds, as pure functions that run in Node: the presentation table (layout, measure, contents, neighbour rule, empty text, link labels), `tableOfContents` (Astro's own headings, depths 2 and 3, at least three entries, never the title), `readingContext` (previous, next, sequence, related, chapters), `entryReferenceIssues` and `groupIndex`. Neighbours: Blog, Timber Logs and Months' Original by their index order, oldest to newest; Trail by `position` within a series; Kosmos by `position` or `chapterNumber` within a work, the work's own entry (neither) apart; Book Club by session date within one book; Greenhouse and Berries none. Drafts are never neighbours. "Lesson N of M" appears only when the published lessons are numbered 1 to M without a gap. Index groups: Timber Logs and Months' Original by year, Trail by series (standalone last), Kosmos by work, Book Club by book (most recently discussed first).

**D-097.** The study is `/_design/editorial/` (an overview, an index and article pages for each collection: 30 pages), drawn with the production components. Its fixture, `src/design/editorial-fixture.ts` and the Markdown in `src/design/editorial/`, is synthetic, labelled so, and outside `src/content/`; only `src/design/` and the study's pages import it (EDIT-019). Links on a study page are rebased to the study. `FolderPage` takes an optional `path` that draws the folders of a registered URL; only studies use it, and normal selection follows the page's own URL as before. Like the other studies, these pages are a deployment matter (D-005): they are all under `dist/_design/`, nothing links to them from a real page, no sitemap or feed exists, and the whole directory can be left out of a published build. The smoke test's ceiling for all studies is now 1,000,000 bytes (was 600,000). Nothing was published, and no deployment file changed.

### D-098 to D-103 — Quarto and scientific publishing (P13)

**D-098.** Quarto may take no ownership of the website: no navigation, URL, folder, collection overview, global CSS, palette, page shell or deployment. A source `science/<dir>/<name>.qmd` (dir: `greenhouse`, `trail`, or `design` for the study) yields one entry `src/content/<dir>/<name>.md`, generated, holding only the metadata the source's front matter states and the collection's schema accepts. Quarto options are a fixed list (`bibliography`, `csl`, `engine`, `jupyter`, `execute`, `lang`, `link-citations`, `format`); every other key is the entry's. The literary collections, Blog, Berries and Timber Logs are not enabled. Ordinary Markdown stays the default, and no file was converted. Not changed: P10's schemas, routes and ordering, P12's layouts, indexes and shell, the folders, the palettes, the CV and P11 (a bibliography is not a publication record).

**D-099.** One document (equation, figure, table, citation, footnote, callout, code) was rendered to HTML and to GFM Markdown. GFM keeps no figure or table semantics, needs a math runtime, and loses code output and callouts, so HTML was chosen (the comparison is in `planning/architecture.md`). `format.html.minimal` was tried and rejected: it degrades callouts to blockquotes. The settings are in `science/_quarto.yml`: MathML, no code-copy, no hover scripts, SVG figures. Pandoc's default author-date citation style is used; a `.csl` can be added per document. The tool, `scripts/science.mjs`, has `check`, `verify`, `render` and `execute`; `npm run build` is now `node scripts/science.mjs verify && astro build`, which executes nothing and needs neither Quarto nor Python. Tested with Quarto 1.10.19 (Pandoc 3.10.0) and Python 3.12.13 with ipykernel 7.3.0, jupyter_core 5.9.1, nbformat 5.10.4, nbclient 0.11.0 and pyyaml 6.0.3 (`science/environment.txt`); CI that renders should pin a 1.10 release, CI that builds needs none of them. No TeX, R, Julia, Docker, Conda environment or PDF output was set up.

**D-100.** `ultrahtml` 1.7.0 is added as an exact development dependency: the parser Astro already depends on and had installed. It is imported by `scripts/science-html.mjs` and the tests only. The extractor keeps an allowlist of tags, attributes and MathML, removes Quarto's title block, copy buttons, scripts and styles, turns table-alignment styles into classes, moves section ids to their headings, removes random caption identifiers, and fails on a `<h1>`, a script, an event handler, a `style`, an unknown tag, an unsafe URL, an external or escaping image, an image without alt text, a duplicate id, a link without a target or an unresolved reference or citation. SVG figures are also checked for scripts and external references. Sources are trusted owner-authored material rendered locally; nothing is accepted from anyone else.

**D-101.** Pandoc's MathML is used: numbered display equations, inline mathematics, Greek letters, TeX kept in an `annotation` for assistive technology. The page loads nothing for it. MathML is drawn by the browser's own engine, so the look differs a little between browsers (KL-65).

**D-102.** `science:execute <dir>/<name>` is the only command that runs code, for one document; there is no "all". `science:render` passes `--use-freezer` for a document with code (`--no-execute` otherwise) and refuses when the code differs from what was executed. Rendering succeeds with no Python at all, which the tests use as the proof that nothing ran. Quarto's `freeze` is a convenience here, not a safeguard: it is ignored for a single-file render without `--use-freezer`. The explicit path rules, the fixed name pattern and the argument-list process calls are the safeguards; an execution has the owner's own rights, so only the owner's code is executed.

**D-103.** Committed: sources, bibliographies, `_quarto.yml`, `science/_freeze/` (small), the generated article, entry, figures and `src/science/manifest.json`. Ignored: `science/_build/`, `science/.quarto/`. The manifest has the SHA-256 of every input, of the code cells, of the frozen results and of every output, and the tool versions of the last execution; no timestamp. The committed generated tree of the test fixture is regenerated and compared with the tool's output by `tests/science-execute.mjs`, so it cannot drift. The synthetic specimen (`/_design/quarto/`, `/_design/quarto/markdown/`) and its figure sit under `_design/`, like the other studies; deployment (D-005) may leave them out. Not done, by design: the authoring CLI (P14), PDF output, R or Julia, a citation import, a mapping from citations to records.

### D-107 to D-111 — Authoring workflow (P14)

**D-107.** One small command-line tool, five npm scripts: `content:new`, `content:validate`, `content:preview`, `content:publish`, `content:archive` (`scripts/content.mjs`, over the engine `scripts/content-lib.mjs`). Node.js, no new dependency (`node:util` parses arguments); every command takes explicit arguments and asks nothing; `--root <dir>` points at another project folder, which is how the tests run on throwaway ones; `--json` prints validation findings as data. Shared definitions are one erasable-TypeScript module, `src/editorial/authoring.ts`: the formats each collection accepts, the per-collection fields, the templates, the command list and the check list. It declares no collection (identities, directories and owners stay in `src/editorial/collections.ts`, metadata rules in `src/editorial/schema.ts`), and a test creates every collection's template and validates it against the real schema. A Python CLI was not chosen: Node is already required. None of the five commits, pushes, deploys, deletes, or runs a notebook cell; there is no delete command, by design.

**D-108.** The author's file is the one source. A Markdown article is `src/content/<dir>/<slug>.md`; a Quarto article is `science/<dir>/<slug>.qmd`, and its generated registration (`src/content/<dir>/<slug>.md`, marked `GENERATED`), fragment and figures are derivatives that no command edits as a source (a hand-written entry beside a `.qmd` is an error; a hand-edited registration is reported). Quarto is offered for The Greenhouse and Bearnard's Trail only (D-098), and a test compares that list with `scripts/science.mjs`. New articles are `status: draft` with no date: nothing is invented. A Quarto draft is registered when it is created (a render that computes nothing), because P13 fails the build for an unregistered source (D-103); if Quarto is missing, creation is refused, and if registration fails the new file is removed again. The slug is suggested from the title once; after that it is the author's and never follows the title. `publish` needs `--date YYYY-MM-DD` or `--today`, shows the exact lines it would change, and writes only with `--yes`; it changes the `status:` and `publishedAt:` lines in place and nothing else, never rewrites a date that exists, and refuses anything but a draft. `archive` changes `status:` to `archived` and nothing else, and refuses anything but a published article. For a Quarto source both re-register the article afterwards and put the source back if that fails. Publishing is a change to a source, not a deployment; no command touches git.

**D-109.** One preflight, `analyze()` in `scripts/content-lib.mjs`, serves `validate`, `preview` and `publish`; it reuses the build's own functions (schema, `collectionIssues`, `entryReferenceIssues`, `recordReferenceIssues`, `createNavigation` for address collisions, P13's `verify` for Quarto freshness) and adds what a build does not check: link and resource paths, headings, placeholders, local paths and demonstration markers, a public entry relating to a draft, and a changed slug. The checks are one list (`PREFLIGHT_CHECKS`), each `error`, `critical` or `warning`; a `critical` check is a warning for a draft and an error for an entry that is, or is about to be, public, so a draft in progress is never blocked by what publication will require. Publication checks the entry in the state it would have after the change, before any byte is written. A Quarto article whose generated copy is stale, missing, hand-edited or whose code was not executed is an error for every status, since P13 stops the build on it. A published or archived entry whose slug differs from the last commit is an error (a changed address is a migration, which has no redirect system yet). The tool checks that an article is technically ready, never that it is right.

**D-110.** The Publishing Workbench is a read-only, development-only part of the site: `/_design/publishing/` (an overview), `/_design/publishing/workflow/` (the real commands run on a throwaway synthetic article, with their output, text committed in `src/design/publishing/workflow-transcript.txt` and regenerated and compared by `tests/authoring.mjs`) and `/_design/publishing/draft-example/` (a synthetic draft drawn by the real Greenhouse layout). Its collections, commands and checklist are drawn from the same lists the CLI uses. It has no control that changes a file. It is routed only when `demosEnabled()` is true (the dev server and `npm run demo:build`, D-105); `npm run build` leaves it out, and the release search (`scripts/demo-check.mjs`) fails on a workbench path or marker. It is linked from the Greenhouse Overview, inside the Development Demonstrations section, so no URL has to be typed; it adds no folder, tab or row. The synthetic example is not an entry: it lives in `src/design/`, which no loader reads, and nothing from it enters `src/content/`, `public/` or a release.

**D-111.** Convention, strengthening D-106: owner-facing visual functionality must be inspectable in the normal local website, reached by clicking, before a milestone is considered visually complete; a hidden design-study URL is not enough. Also recorded: drafts are absent from every build but, once a draft file is committed, its text is in the public repository (`development/authoring-guide.md`); the development server is a preview, not a confidentiality boundary. Not done, by design: a web editor, a database or any server-side write; a delete command; URL migration and redirects; a slug-rename command; an `updatedAt` bump (the author writes it); automatic commit, push or deploy.

### D-118 to D-121 — World clocks (P16)

### D-130 to D-136 — The 3D nucleus prototype (P19)

**D-130.** The nucleus is built with Three.js, pinned exactly (`three` 0.187.0 and `@types/three` 0.187.0, the two dependencies P19 adds), in WebGL, procedural geometry and plain TypeScript: no React Three Fiber, no physics engine, no asset loading, no new router. It is a scientifically informed artistic model of interphase chromatin: a translucent envelope, twelve chromosome territories each one continuous folded polymer, more compact chromatin near the envelope, and one yellow region of one polymer. It is deterministic (a seeded generator, `SEED` in `src/visualization/nucleus/config.ts`). It is not a reconstruction of a cell, a measured genome, a molecular-dynamics simulation or a calibrated model, and must never be described as one; no pores, histones, nucleolus or organelles are drawn, and no condensed (metaphase) X-shaped chromosomes. The code is `src/visualization/nucleus/` (twelve small modules; the pure ones, `model`, `tube`, `deformation`, `view`, `config`, `types`, `fallback`, `interaction`, import neither Three.js nor the DOM, so they are tested in Node.js). Three.js is imported only by `materials.ts` and `renderer.ts`, which `mountNucleus` loads on demand.

**D-131.** Rendering. The resting chromatin is one merged opaque, lit, vertex-coloured mesh and the highlighted strand its own mesh, so strands never sort against each other and depth reads through lighting and a pale fog; the envelope is two translucent, depth-write-free layers (inside faces with a faint fill, outside faces with a fresnel rim) drawn after the chromatin, so the strands always show through and no sorting error can hide one. Four draw calls, three materials, about 128,000 triangles at full detail and 78,000 at `light` (touch-oriented devices). The camera is perspective (30°), stationary, framed from the frame's aspect so the nucleus is never clipped; the nucleus is turned inside its group so depth reads. The renderer's pixel ratio is capped at 2 (1.5 on touch-oriented devices). The object's colours (pale periwinkle, lavender, sage and blush territories, a yellow region) are its own, in `config.ts`; they are not site tokens, appear in no stylesheet, and the five locked palettes and the Home folder are untouched (D-076).

**D-132.** The deformation is one continuous state: an activation and a direction-and-reach, each critically damped with the exact step (ω 3.8 rad/s: about a second to 90 %, 2.3 s to settle; no overshoot). Pointing, retargeting and releasing change only what the state heads for; it is never reset, so the shape always moves on from where it is. The region's control points are displaced by `sin²` weights that are zero, with zero slope, at both anchored ends: each moves toward an "opened" shape (its loops extended from the local average of its neighbours) and reaches up to 0.32 model units toward the target on screen, a little toward the viewer, and is kept inside the envelope by a continuous scale-back. One strand's positions and normals are rewritten in place each frame; no geometry is created, replaced or hidden and no colour changes. A target is a page position; it becomes half-frame units, and the response runs from where the region appears to where the target is, with a reach that saturates (`tanh`), so every target moves the same anchored region and a distant target asks for no more than a near one.

**D-133.** The integration contract for P20 is `mountNucleus(element, options?)` returning a `NucleusController` (`setTarget`, `release`, `refresh`, `diagnostics`, `dispose`), and `observeTargets(controller, elements)`. The latter listens, passively, for `pointerenter`/`pointerleave` (mouse and pen) and `focusin`/`focusout` on the given elements and never cancels or stops an event or alters the element, so a real tab keeps working exactly as it does. The lifecycle (`lifecycle.ts`) draws on demand: once at the start, once per resize or restore, and only while the response is moving; it pauses while the page is hidden, redraws on `pageshow`, handles WebGL context loss (a restore redraws; no return within 2.5 s gives the fallback), and `dispose()` releases the renderer, geometry, materials, listeners, observer, frame and timer. Mounting again on one element replaces the old mount. The homepage's own navigation, previews and clocks are not touched by any of it.

**D-134.** Interactive or still. A device whose pointer can hover and that asks for no reduced motion gets the interactive nucleus. A touch-oriented device (`(hover: none), (pointer: coarse)`) and a visitor who prefers reduced motion get a still nucleus: a real 3D render of the resting state, drawn once, never animating, ignoring targets, not listening for touch, with `pointer-events: none` and `touch-action: auto` on the canvas so scrolling and links are untouched. A preference that changes while the page is open is followed without a reload. The nucleus is never a navigation control: the page is complete without it.

**D-135.** The fallback is a still picture drawn from the same model, not another illustration: `fallback.ts` projects the strands and the envelope's silhouette into about 13 SVG paths, `NucleusFigure.astro` draws them with no script in a frame of fixed aspect ratio, and the canvas replaces them only when it is live. If WebGL is unavailable, or context is lost for good, the picture stays and the status says `fallback`. It is a provisional capture, flat and without lighting or translucency, to be replaced by an approved capture when the owner approves the nucleus.

**D-136.** The prototype is a development specimen, `/_design/nucleus/` ("3D Nucleus Prototype"), routed only in development and demonstration builds (D-105), reached by clicking from the local homepage's development note and the Site Map & Page Coverage list. It mounts the nucleus through the P20 interface, with five simulated tabs (real buttons that do not navigate), a play button, frame-width presets, a preview of the still nucleus, and a diagnostics panel that can be hidden. Nothing of the real homepage, its stage, its clocks, the folders or the navigation changed. A release build holds no page, no specimen script and no Three.js: the page's script is a one-line guard on the same condition as `demosEnabled()` (`src/scripts/nucleus-specimen.ts`, the only other reader of the mode, because a bundler folds a comparison of constants but not a function call), and the output is searched for the page, its markers and `WebGLRenderer` (`scripts/demo-check.mjs`). ### D-145 to D-150 — Scheduling (P21)

**D-145.** The provider and the configuration. Scheduling is delegated to an external provider, **Cal.com**, through its public booking link; the site stays static and gets no booking database, email service, authentication, serverless function or API key. The provider is chosen on documented capabilities (a monthly inline embed, host approval, pending holds, booker verification, calendar sync, a hosted page), none of which is configured or tested, because the owner has no account (`development/scheduling-guide.md` keeps documented, configured and tested apart). **D-146.** The availability file. The owner's availability will come from one file, whose path is the one configured field `availabilitySourcePath` (`repo:<relative path>` or `env:<NAME>`; never absolute, never under a public, generated, page or CV folder, never a client-exposed variable). Until the file exists the provider's own schedule is the temporary authority, and with no approved link the page offers no times.

**D-147.** The embed. The monthly calendar (`layout: "month_view"`) is loaded by `src/scheduling/embed.ts` (testable in Node with a stand-in browser) and bound by `src/scripts/schedule-embed.ts`, rendered by `ScheduleEmbed.astro` only when scheduling is ready, so no other page and no unconfigured Schedule page ships any scheduling code. No Content-Security-Policy is deployed: GitHub Pages sends no response headers and a `<meta>` policy cannot carry frame rules, so the narrow origin is enforced in code; if a policy is ever added, the provider needs `app.cal.com` for scripts and frames, and any other origin it needs is **unverified**. **D-148.** Time zones.
