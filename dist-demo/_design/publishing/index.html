Publishing Workbench

Articles are text files. You write one in your editor, five commands create, check, publish and archive it, and the site builds the rest. Nothing on this page edits a file: it shows what the commands do, in the words and with the same lists the commands use.

The lifecycle

Draft → Validation → Published → Archived

  • draft

    Being written. Previewable with the dev server; no page, no listing and no link in a build.

  • published

    Has its page and its place in the collection's index.

  • archived

    Kept for the record and marked as historical. Same address, same date, still listed.

The state is a line in the article's metadata. Publishing an article changes that line; it does not put anything on the web. The site goes live only when the repository is built and deployed, which is a separate step you take on purpose.

The commands

Five commands, run from the project folder. Each takes explicit arguments and asks nothing.

content:newwrites one source file

Create a draft: a Markdown file, or a Quarto source with its registration.

npm run content:new -- --collection greenhouse --title "My Article"
npm run content:new -- --collection greenhouse --format qmd --title "My Scientific Tutorial"
content:validatechanges nothing

Check one article, or all of them. Changes nothing.

npm run content:validate -- --all
npm run content:validate -- --collection greenhouse --slug my-article
content:previewchanges nothing

Show where an article is, its state, and its local address. Changes nothing.

npm run content:preview -- --collection greenhouse --slug my-article
content:publishwrites one source file

Check a draft as it would be published and show the change; with --yes, make it.

npm run content:publish -- --collection greenhouse --slug my-article --date 2026-11-20
npm run content:publish -- --collection greenhouse --slug my-article --date 2026-11-20 --yes
content:archivewrites one source file

Mark a published article as archived; its address and date stay. With --yes, make it.

npm run content:archive -- --collection greenhouse --slug my-article
npm run content:archive -- --collection greenhouse --slug my-article --yes

publish and archive only show their change until you add--yes. None of the five commits, pushes, deploys or runs a notebook cell.

The publication checklist

content:validate and content:publish run these checks, and only these. They are one list in the code; this is that list. They show that an article is technically ready, not that it is right: scientific accuracy and editorial approval are yours.

metadata

  • metadata.syntaxThe front matter exists and is valid YAML, with real calendar dates.always blocks
  • metadata.schemaThe metadata satisfies the collection's schema: known fields, a supported status, a valid slug, the collection's own required fields.always blocks
  • metadata.publicationA published or archived entry has a description and a publication date.blocks publication; a warning in a draft

identity

  • identity.slugThe slug is unique in its collection, and order fields (position, chapter) are not shared.always blocks
  • identity.routeThe public address does not collide with a folder or another page.always blocks
  • identity.sourceThere is one authoritative source: no hand-written entry beside a Quarto source, and a generated registration is never edited.always blocks
  • identity.stableA public entry's slug is unchanged since the last commit: a changed address is a migration, not an edit.always blocks
  • identity.filenameThe file name matches the slug.reported, never blocks

relationships

  • relationships.entriesEvery related entry exists, and none is the entry itself.always blocks
  • relationships.recordsEvery canonical record the entry names exists.always blocks
  • relationships.publicA public entry relates only to public entries: a draft is never recommended.blocks publication; a warning in a draft

markdown

  • markdown.heading-levelThe body has no level-1 heading: the title is the page's one.always blocks
  • markdown.heading-orderHeading levels do not skip.reported, never blocks
  • markdown.linksInternal links point at pages of the site, and are written from the site root.blocks publication; a warning in a draft
  • markdown.resourcesImages and files named by a site path exist in public/.blocks publication; a warning in a draft

quarto

  • quarto.freshnessThe generated article is current with its source: not missing, stale or edited by hand.always blocks
  • quarto.executionCode in a source has been executed in its current form (only the explicit execute command runs it).always blocks
  • quarto.referencesThe rendered article has no unresolved cross-reference or citation.blocks publication; a warning in a draft

safety

  • safety.placeholdersNo authoring placeholder (TODO, FIXME, TBD, XXX, lorem ipsum) is left in the text.blocks publication; a warning in a draft
  • safety.localNo local file path or localhost address is in the text.blocks publication; a warning in a draft
  • safety.syntheticA real entry is not a demonstration: no synthetic marker in its metadata or text.always blocks

Why things look the way they do

An article is valid but not published
Validation answers “is it well formed?”; publication is a decision. A draft can pass every check and stay a draft until you run content:publish.
A Quarto article is stale
The page shows the article that was generated from the .qmd. Edit the source and the generated copy is out of date, so the build refuses it until you runnpm run science:render -- <dir>/<name>. That re-renders and computes nothing. Code is run only by npm run science:execute, and only when you name the document.
A draft is on screen here but not in production
The dev server shows drafts so you can read them as a reader will. A build routes only published and archived articles, so a draft has no page, no index entry and no link in anything that is deployed.
A draft in the repository
The repository is public. A draft is absent from the website but its text is in the repository once you commit it. Keep anything you do not want read out of committed files.
