## Causes found and repaired (evidence in the run reports and `qa-report-*` artifacts)

1. **A shallow checkout.** `actions/checkout` fetches one commit, and the preservation guards diff against fixed earlier commits: five checks failed ("bad revision") and 27 guards were SKIPPED. Reproduced in a local depth-1 clone. Repaired with `fetch-depth: 0` and a new environment check, **QA-ENV-06**, that fails a shallow clone with the fix in its message (`QA-HISTORY-01` tests it against a real depth-1 clone and its unshallowed twin).
2. **No pointing device.** Chrome on the runner reports `pointer: none` and `hover: none`, so the pages correctly behave as for a touch visitor (still nucleus; Home's sticky tab row needs `(hover: hover) and (pointer: fine)`). Thirteen checks written for a mouse failed. Reproduced locally with the same Chrome setting (the same nucleus checks failed), repaired by stating a desktop mouse in the harness (`--blink-settings`); both nucleus suites then passed locally, and touch emulation still overrides it.
3. **Click geometry.** A link that wraps was clicked at the middle of the box around all its lines (QTO-030B, the scheduling click helper). They click the first line box now.
4. **Fixed waits.** The touch-swipe checks slept 600 ms; the clocks check read `--:--` before the page's script had filled them (A11Y-CLOCKS). They wait for the state.
5. **Clicks into a view transition.** Right after a navigation, the 140 ms cross-fade (D-071) takes hit-testing away from the page: `elementFromPoint` returns `html` over a tab that is exactly where the click goes (evidence: the click records of PREV-013 and AUTH-031). The harness's wait looked only at the transition's animations, which exist after its object (`document.activeViewTransition`) does. Measured locally at 1x, 4x and 8x CPU: the object is present at every arrival and gone within 200 ms, and hit-testing is normal after that in 54 of 54 samples. `viewTransitionOver()` waits for both. **Confirmed on GitHub (run 4):** PREV-013 and the QA-INSPECT-01 flake no longer fail; AUTH-031 could not be judged, because the suite stalled.
6. **Touch gestures.** Chrome's synthesized touch scroll did nothing on the runner, upwards or sideways (the same checks pass on the Mac). The shared helper `touchSwipeScrolls` tries it first and raw touch events second, says which worked, and fails when neither moves anything. The vertical checks (NUC-033B, NUCINT-033B's first step) pass on GitHub with it. **The sideways swipe over the tab row (NUCINT-033B's last step) still fails there by both ways** (run 4: the row scrolls, `scrollWidth` greater than `clientWidth`, and neither the synthesized gesture nor raw touch events moved it): the cause is not found. The failure message now records what the swipe reached and the row's computed `touch-action` and overflow. One observation, not a cause: after touch emulation is switched off the runner's pointer features read `none` again, not the desktop mouse the harness states, so a check that ran after a touch test on the runner would see no hover; the touch tests are the last in their suites by design.
7. **Silent stalls.** A Chrome command that is never answered waited for ever. Each now fails after 120 s and names the command.

## Real defect found and repaired

**A scrolling table that the keyboard cannot reach (WCAG 2.1.1).** `.ed__body table` is a scrolling box (`display: block; overflow-x: auto`). On a runner whose wider fallback font made the table in the Quarto demonstration overflow, axe-core reported `scrollable-region-focusable`. It could happen to any reader with a wide font, and was invisible on the Mac only because its font is narrow. Quarto `<table>` elements now get `tabindex="0"` like `<pre>` (`EditorialEntry.astro`), and `QA-A11Y-01` checks the markup of the demonstration article whatever the font. **Not covered:** a table in a plain Markdown entry (no published or demonstration entry has a wide one). Covering it needs a rehype step in the Markdown pipeline, which is not installed; recorded here, not done.

## The five checks measured with macOS fonts (second part of P22-A01)

The owner chose to rewrite them as font-independent rules, not to skip them. `QA_LINUX_FONTS_DIR` (below) draws the test browser the way the runner draws it, which made the work checkable on a Mac; with it, and before any change, the five checks failed with the runner's numbers.

- **`RESP-015`: rewritten.** What a font cannot move stays exact (the shell's left and width, the paper's width; the h1's distance below the paper's top edge and the seam between the last row and the paper, which are the folders' own padding and were identical in Seravek and DejaVu Sans). What it moves is not pinned: the rows' heights above the paper (so the h1's page position), and whether eleven labels fit one row. Instead, per row: tabs in left-to-right order, the global row in the registry's order, every label inside its tab, **the row fits or it scrolls**, and every tab can be brought into the row and is the element under the pointer there; the h1 reads whole (inside the paper, not clipped, nothing overlapping it); no page overflow; and wider than 1440 px the global row has the same room as at 1440 px. Injecting three defects (a row that cannot scroll, a tab out of order, a page that scrolls sideways) makes it fail each time. It records what the row did (fits on the Mac, scrolls in DejaVu Sans).
- **`NUCINT-041B`: rewritten.** The tab row's four numbers, the welcome's x, y and width and the frame's x, width and height stay exact (identical in both fonts). The welcome's height and the frame's y, which follow the text, became relations: the welcome holds its content, the regions are in P15's order and do not overlap, the page does not scroll sideways.
- **`P13A-029` and `P13A-029B`: a real defect, repaired in the implementation.** The "Publishing Workbench" link sits inside a sentence; its tappable box was the font's glyph box (about 18.6 px at 16 px in DejaVu Sans), under the 20 px these checks require. `[data-workbench-link] a` has `padding-block: 0.25em` now: the box that can be tapped is taller, no line moves. Both checks pass with Mac fonts and with DejaVu Sans, unchanged.
- **`CLOCK-034B`: a genuine layout defect that needs the owner's decision. The check was not changed.** It was never Mac-specific: it compares each clock before and after the script fills it. Measured with the layout as it is: with Mac fonts a typical date is stable, but the longest date ("Wednesday, 30 September", and any date whose weekday and month names are long) already makes the first two clocks grow from 64 to 100 px at 1440 px when filled; with DejaVu Sans every date does (64 to 75 on the runner, 64 to 100 under the emulation). The cause is the date: the reading column is as wide as its widest line, so the date widens it when it arrives, and the place text beside it ("Alaska, United States") re-wraps, a line or two. Every layout that holds for every date and every font changes the approved look of the clocks (P16, D-118 to D-121), which is a recorded decision, not a side effect of a test repair. Tried and measured: reserving the widest date's width (stable, but "Anchorage" breaks mid-word and "Mexico City" wraps on the Mac at 1440 px; reverted), a threshold in the digits of the clock's own font (does not separate the cases: the Mac at 1440 px is narrower in digits than DejaVu at 1024 px). Options for the owner: (a) in the 2-column desktop widths put the reading (time and date) beneath the place text; (b) show the short date ("Mon, 16 Nov") where the clock is narrow; (c) one clock per row at desktop. Adding the long-date instant to the check is the acceptance test of whichever is chosen. Until then it fails on the runner, and the long date's failure on the Mac is not in the check.

## Open, with the cause established

- **`NUC-050` (software-WebGL frame time).** The ceiling is a 100 ms median frame. Measured: the Mac 66.6 ms (53 frames in 3 s; an earlier note of this record that said "about 20 ms" was wrong), the runner 100.0, 133.3, 83.3 and 99.9 ms in runs 2 to 5 (24 to 41 frames). Cause: Chrome draws about 128 000 triangles with SwiftShader on the CPU; on a shared 4-core runner a frame takes five to eight 16.7 ms steps, so the median sits on the ceiling and falls on either side of it. It measures the machine. Decision for the owner: a separate, documented ceiling for CI (the runner measured up to 133 ms; 200 ms would leave headroom), or accept the flicker. The check was not changed.
- **`NUCINT-033B`, the sideways swipe over the tab row.** Run 5: the swipe starts on a tab's link (`a.gl-folder-tab__label`), the row can scroll (`scrollWidth` 1191, `clientWidth` 341, `touch-action: auto`, `overflow-x: auto`), and neither the synthesized gesture nor raw touch events moved it. The vertical swipes pass. Suspect, not proven: on Linux a touch that starts on a link is held for a drag. Run 6 added that no point of the row is free of a link (every tab is one big link), so there is no empty part to swipe on. The check now swipes on a link as before and, if that does not move the row, on the same link with the browser's link dragging switched off, says what each did, and passes if the row can be moved by touch at all. If only the second moves it, the cause is the drag and a phone is not affected by it; that is for the real-device review (P23) to confirm.

## Found since, and repaired

- **The two dev-server suites never exited, so the orchestrator killed them after 900 s and called them failed.** `demo-dev-browser` and `authoring-browser` start `astro dev`. On a Mac `npx astro dev` hands off to a detached child and exits, which closes the pipe the test reads; on the GitHub runner it stays attached, and the pipe kept the test process alive after every check had passed (authoring: three PASS lines and the summary; demo-dev: both PASS lines and the summary; the heartbeat showed the last Chrome command answered and no new one). A failing run always ended with `process.exit(1)`, a passing one never did, which is why the stall appeared only once the checks passed (never in run 1, when AUTH-031 failed). The stalled suite's dev server then stayed running and the next attempt of the same suite, and the other dev-server suite, reported "the dev server did not start" (the NOT RUN of runs 2 to 6). An earlier version of this record read the stall as a hang inside the tests: that was wrong, I had filtered the PASS lines out of the logs I read. `finish()` now ends the process after a passing run (the exit handler stops the server), and `QA-EXIT-02` guards it. **Confirmed on the runner (run 7):** both suites pass and the whole browser job takes 17.7 minutes.

- **`previews-browser` could not start Chrome on its first attempt (run 5).** A cold start on a fresh runner; the harness waited 10 s for Chrome's port file. It waits for the port file for up to a minute now (a state, not a time).
