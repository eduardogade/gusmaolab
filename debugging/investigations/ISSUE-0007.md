## Causes found and repaired (evidence in the run reports and `qa-report-*` artifacts)

1. **A shallow checkout.** `actions/checkout` fetches one commit, and the preservation guards diff against fixed earlier commits: five checks failed ("bad revision") and 27 guards were SKIPPED. Reproduced in a local depth-1 clone. Repaired with `fetch-depth: 0` and a new environment check, **QA-ENV-06**, that fails a shallow clone with the fix in its message (`QA-HISTORY-01` tests it against a real depth-1 clone and its unshallowed twin).
2. **No pointing device.** Chrome on the runner reports `pointer: none` and `hover: none`, so the pages correctly behave as for a touch visitor (still nucleus; Home's sticky tab row needs `(hover: hover) and (pointer: fine)`). Thirteen checks written for a mouse failed. Reproduced locally with the same Chrome setting (the same nucleus checks failed), repaired by stating a desktop mouse in the harness (`--blink-settings`); both nucleus suites then passed locally, and touch emulation still overrides it.
3. **Click geometry.** A link that wraps was clicked at the middle of the box around all its lines (QTO-030B, the scheduling click helper). They click the first line box now.
4. **Fixed waits.** The touch-swipe checks slept 600 ms; the clocks check read `--:--` before the page's script had filled them (A11Y-CLOCKS). They wait for the state.
5. **Clicks into a view transition.** Right after a navigation, the 140 ms cross-fade (D-071) takes hit-testing away from the page: `elementFromPoint` returns `html` over a tab that is exactly where the click goes (evidence: the click records of PREV-013 and AUTH-031). The harness's wait looked only at the transition's animations, which exist after its object (`document.activeViewTransition`) does. Measured locally at 1x, 4x and 8x CPU: the object is present at every arrival and gone within 200 ms, and hit-testing is normal after that in 54 of 54 samples. `viewTransitionOver()` waits for both. **Confirmed on GitHub (run 4):** PREV-013 and the QA-INSPECT-01 flake no longer fail; AUTH-031 could not be judged, because the suite stalled.
6. **Touch gestures.** Chrome's synthesized touch scroll did nothing on the runner, upwards or sideways (the same checks pass on the Mac). The shared helper `touchSwipeScrolls` tries it first and raw touch events second, says which worked, and fails when neither moves anything. The vertical checks (NUC-033B, NUCINT-033B's first step) pass on GitHub with it. **The sideways swipe over the tab row (NUCINT-033B's last step) still fails there by both ways** (run 4: the row scrolls, `scrollWidth` greater than `clientWidth`, and neither the synthesized gesture nor raw touch events moved it): the cause is not found. The failure message now records what the swipe reached and the row's computed `touch-action` and overflow. One observation, not a cause: after touch emulation is switched off the runner's pointer features read `none` again, not the desktop mouse the harness states, so a check that ran after a touch test on the runner would see no hover; the touch tests are the last in their suites by design.
7. **Silent stalls.** A Chrome command that is never answered waited for ever. Each now fails after 120 s and names the command.

## Real defects found and repaired

**A scrolling table that the keyboard cannot reach (WCAG 2.1.1).** `.ed__body table` is a scrolling box (`display: block; overflow-x: auto`). On a runner whose wider fallback font made the table in the Quarto demonstration overflow, axe-core reported `scrollable-region-focusable`. It could happen to any reader with a wide font, and was invisible on the Mac only because its font is narrow. Quarto `<table>` elements now get `tabindex="0"` like `<pre>` (`EditorialEntry.astro`), and `QA-A11Y-01` checks the markup of the demonstration article whatever the font. **Extended to Markdown entries (D-160, owner's question of 2026-11-23):** the HTML Astro rendered from a Markdown entry (`entry.rendered.html`) goes through the same in-memory step, so a wide table written in Markdown is reachable too; a rehype plugin was the other route and needs `@astrojs/markdown-remark`, which Astro 7 no longer installs. The built demonstration output differs from before only by `tabindex="0"` on the two Markdown tables. QA-A11Y-01 now checks both demonstration Markdown articles, which hold tables. Not covered: the development specimens that import `.md` directly (KL-130). The price is one extra tab stop for a table that never scrolls.

**The clocks' reading column moved when the date arrived (CLOCK-034B).** Below, repaired by the owner's decision D-158.

## The five checks measured with macOS fonts (second part of P22-A01)

The owner chose to rewrite them as font-independent rules, not to skip them. `QA_LINUX_FONTS_DIR` (below) draws the test browser the way the runner draws it, which made the work checkable on a Mac; with it, and before any change, the five checks failed with the runner's numbers.

- **`RESP-015`: rewritten.** What a font cannot move stays exact (the shell's left and width, the paper's width; the h1's distance below the paper's top edge and the seam between the last row and the paper, which are the folders' own padding and were identical in Seravek and DejaVu Sans). What it moves is not pinned: the rows' heights above the paper (so the h1's page position), and whether eleven labels fit one row. Instead, per row: tabs in left-to-right order, the global row in the registry's order, every label inside its tab, **the row fits or it scrolls**, and every tab can be brought into the row and is the element under the pointer there; the h1 reads whole (inside the paper, not clipped, nothing overlapping it); no page overflow; and wider than 1440 px the global row has the same room as at 1440 px. Injecting three defects (a row that cannot scroll, a tab out of order, a page that scrolls sideways) makes it fail each time. It records what the row did (fits on the Mac, scrolls in DejaVu Sans).
- **`NUCINT-041B`: rewritten.** The tab row's four numbers, the welcome's x, y and width and the frame's x, width and height stay exact (identical in both fonts). The welcome's height and the frame's y, which follow the text, became relations: the welcome holds its content, the regions are in P15's order and do not overlap, the page does not scroll sideways.
- **`P13A-029` and `P13A-029B`: a real defect, repaired in the implementation.** The "Publishing Workbench" link sits inside a sentence; its tappable box was the font's glyph box (about 18.6 px at 16 px in DejaVu Sans), under the 20 px these checks require. `[data-workbench-link] a` has `padding-block: 0.25em` now: the box that can be tapped is taller, no line moves. Both checks pass with Mac fonts and with DejaVu Sans, unchanged.
- **`CLOCK-034B`: a genuine layout defect that needs the owner's decision. The check was not changed.** It was never Mac-specific: it compares each clock before and after the script fills it. Measured with the layout as it is: with Mac fonts a typical date is stable, but the longest date ("Wednesday, 30 September", and any date whose weekday and month names are long) already makes the first two clocks grow from 64 to 100 px at 1440 px when filled; with DejaVu Sans every date does (64 to 75 on the runner, 64 to 100 under the emulation). The cause is the date: the reading column is as wide as its widest line, so the date widens it when it arrives, and the place text beside it ("Alaska, United States") re-wraps, a line or two. Every layout that holds for every date and every font changes the approved look of the clocks (P16, D-118 to D-121), which is a recorded decision, not a side effect of a test repair. Tried and measured: reserving the widest date's width (stable, but "Anchorage" breaks mid-word and "Mexico City" wraps on the Mac at 1440 px; reverted), a threshold in the digits of the clock's own font (does not separate the cases: the Mac at 1440 px is narrower in digits than DejaVu at 1024 px). Options for the owner: (a) in the 2-column desktop widths put the reading (time and date) beneath the place text; (b) show the short date ("Mon, 16 Nov") where the clock is narrow; (c) one clock per row at desktop. Adding the long-date instant to the check is the acceptance test of whichever is chosen. Until then it fails on the runner, and the long date's failure on the Mac is not in the check.

  **Decided and repaired (D-158, option B, 2026-11-23).** The visible date is the short form ("Wed, 30 Sep"), the full date stays as visually hidden text for assistive technology, and an invisible zero-height line of the widest short date ("Wed, 30 May") sizes the reading column in whatever font is drawn, with the date on one line, so the column is as wide before the date arrives as after on every day of the year. CLOCK-034B now measures the list's size and, per clock, the card, city, country and reading boxes and their line counts, before (script off) and after (live), at 320, 390, 768, 1024, 1280 and 1440 px, for four dates (a November Monday; 30 September 2026, where Anchorage is "Wed, 30 Sep" and Auckland "Thu, 1 Oct"; "Wed, 20 May", the widest in a proportional font; "Wed, 1 Jul", the narrowest) and after a minute change: no box moves by more than 0.5 px (sub-pixel rounding; the widest date of the year is up to 0.1 px wider than the sizing line in the Mac's fonts) and no line count changes. CLOCK-034C asserts that no word of a city or country is split across lines and that the date stays on one line, at those widths, at 150 and 200 percent text size from 390 and 768 px, in the Mac's fonts and the runner's; CLOCK-034D that the short date is hidden from the accessibility tree and the full one is in it (read from Chrome's tree); CLOCK-042 that the short date equals an independent calendar table for 9,496 readings. **Negative control:** with the sizing line removed, CLOCK-034B fails with the runner's numbers (the city column 184.8 → 166.6 px). **Reported first, as the owner asked:** at 390 px with text doubled and at 320 px with text at 150 percent the name cannot stay whole in a one-column row (the city column 108.6 px against "Anchorage" at 149.2 px, and 87.5 against 111.9, with the runner's fonts); nothing overflows (KL-132). **A defect of the emulation found on the way:** it did not cover Superclarendon, the homepage's heading font, so a 2 px failure at 390 px and 150 percent was an artifact of DejaVu beside the Mac's wide Superclarendon; the runner's evidence names Liberation Serif for those headings and the emulation now maps Superclarendon to Times New Roman, after which the same check passes with a 45 px margin.

## Decided, with the cause established

- **`NUC-050` (software-WebGL frame time): an environment-aware policy (D-159, owner-approved 2026-11-23).** Cause, unchanged: Chrome draws about 128 000 triangles with SwiftShader on the CPU; on a shared 4-core runner a frame takes five to eight 16.7 ms steps, so a median on one ceiling falls on either side of it (the runner: 100.0, 133.3, 83.3, 99.9 and, in run 8, 133.3 ms; the Mac 66.6 ms). It measures the machine, so it has two thresholds with what each means: 100 ms is the local reference and 200 ms is a CI smoke ceiling that is not an acceptable frame time for the site. Three samples of 2.5 s, each from a nucleus at rest, the median of the medians; at least eight frames per sample; the distribution, the environment (CPU, cores, platform, browser, WebGL renderer, canvas), the verdict and a plain lit-sphere reference workload go to `qa-report/nucleus-frames.json`, the report and the kept artifact whatever the verdict. The deterministic guards are unchanged and are part of the same check (draw calls, triangles, resources, a resting nucleus draws nothing). On the Mac: three sample medians 66.5, 66.6, 66.6 ms, pooled p95 83.4 ms, 136 frames, sphere workload 50.1 ms, ratio 1.33. **A machine-relative budget was considered and is not adopted yet:** it is practical (the workload is 40 lines of raw WebGL), but whether the ratio is the same on the runner and on the Mac is unknown until the runner reports it, and a ratio calibrated on one machine would be a guess on the other. The runs now keep both numbers; with two or three runner results the ratio's spread can be read and the budget changed by a decision.
- **`NUCINT-033B`, the sideways swipe over the tab row: the aim was wrong, and is repaired; the gesture itself is awaiting a runner result.** Run 8's trace (pointerdown/touchstart 2, touchmove 8, pointermove 15, pointercancel 1, `scrollLeft` never above 0) named the first touch's target: `p.welcome__overline`, a paragraph at the top of the page. The measuring had been done, and the page then scrolled on (the fling of the vertical swipe before it ran on), so the point was no longer over the row; the earlier reading of the problem as "a touch that starts on a link is held for a drag" had been a guess on evidence of a mis-aimed gesture. `touchSwipeScrolls` now takes `locate`, a page expression that measures the target, hit-tests the point and reads the start position in one evaluation, and the gesture is sent at once (no delay between validating and dispatching; a raw-touch retry is aimed afresh the same way); a point that is not on the target sends nothing and says so (`targetMissed`). `scrollSettled()` waits for the page's scroll position to stay still for 400 ms before the row is put in the middle of the window and again after it. The check now fails as **TARGETING** (the point was not on the row, or the first touch landed elsewhere, from `firstInRow` in the event trace) apart from "the row did not move"; it keeps every diagnostic (the events that reached the page, the link-dragging and off-link variants), swipes the real row (no synthetic target), and then keeps swiping until the last tab is inside the row's window where a finger would hit it, which checks horizontal scrolling and tab reachability by touch alone. Verified on the Mac, including a probe that a point off the row sends nothing. **If the correctly aimed gesture still fails on the runner, it is a possible real issue and stays open here.**

## Found since, and repaired

- **The two dev-server suites never exited, so the orchestrator killed them after 900 s and called them failed.** `demo-dev-browser` and `authoring-browser` start `astro dev`. On a Mac `npx astro dev` hands off to a detached child and exits, which closes the pipe the test reads; on the GitHub runner it stays attached, and the pipe kept the test process alive after every check had passed (authoring: three PASS lines and the summary; demo-dev: both PASS lines and the summary; the heartbeat showed the last Chrome command answered and no new one). A failing run always ended with `process.exit(1)`, a passing one never did, which is why the stall appeared only once the checks passed (never in run 1, when AUTH-031 failed). The stalled suite's dev server then stayed running and the next attempt of the same suite, and the other dev-server suite, reported "the dev server did not start" (the NOT RUN of runs 2 to 6). An earlier version of this record read the stall as a hang inside the tests: that was wrong, I had filtered the PASS lines out of the logs I read. `finish()` now ends the process after a passing run (the exit handler stops the server), and `QA-EXIT-02` guards it. **Confirmed on the runner (run 7):** both suites pass and the whole browser job takes 17.7 minutes.

- **`previews-browser` could not start Chrome on its first attempt (run 5).** A cold start on a fresh runner; the harness waited 10 s for Chrome's port file. It waits for the port file for up to a minute now (a state, not a time).

- **The dev-server cleanup is proven (D-160, owner's question of 2026-11-23).** The process-exit repair made the Linux stall disappear; it did not show that the servers were stopped. `tests/dev-server.mjs` is the one place a suite starts `astro dev` now: it ends the listeners on the port (`lsof`, or `/proc` where `lsof` is absent) and the process group `npx` started, on exit and on SIGINT, SIGTERM and SIGHUP, waits for the port to close and the group to hold no live process, says `dev server stopped: port N is closed`, and otherwise prints `DEV SERVER LEAK` and fails the suite. QA-DEVSERVER-01 runs a stand-in suite against stand-ins for both ways `astro dev` behaves (handed off to a detached child, as on a Mac; attached, as on the runner), ending by exit, by an error and by SIGTERM, and checks that the port and every process are gone; with the port kill removed from the helper it fails and the helper reports the leak. Both real suites were run locally with process and listener counts before and after: none left. Not covered: SIGKILL (cannot be caught), and the Linux attached behaviour is covered by the stand-in, not by a Linux machine; the runner's own log line (`dev server stopped: …`) will be the first evidence from Linux.

- **A latent defect of the QA command, found by this work: the report could not be written when a failure listed two repository paths.** The first full local run after the guard changes ended with "QA could not run: SyntaxError … JSON.parse". The report is built as JSON and then passed through `redact()` as text, which hid `/home/<name>` and `/Users/<name>` with patterns that took everything up to a space or a slash; the failure message of the nucleus guards listed `"src/components/home/WorldClocks.astro","src/home/clock-time.ts"`, so `/home/WorldClocks.astro","src` was taken for a home directory and the quote and the comma went with it. A run with a failing check that lists files under `src/components/home/` (or under any `/home/`, `/Users/` folder of the repository) could therefore not write `latest.json`, exactly when the report matters. `redact()` now hides a path only where an absolute path begins and never past a quote or a backslash, and `QA-STATE-04` (its redaction half, in `tests/qa.mjs`) round-trips a report that lists those two files, a real home path, a `file://` path and a temporary path.
